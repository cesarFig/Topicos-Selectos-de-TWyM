## Introducción

En esta actividad propongo los documentos que podría consultar un asistente para atender a los clientes de una floristería. Como aún no he desarrollado el Proyecto 1, las políticas y las rutas de API se presentan como ejemplos para el trabajo y deberán definirse al realizar el proyecto.

El recomendador se encargará de decidir si un arreglo necesita cuidado frágil o estándar durante el traslado. Por su parte, el asistente responderá preguntas y consultará los datos que necesite el cliente. Cuando una pregunta requiera una recomendación, tendrá que consultar al sistema encargado de esa decisión.

Para esa decisión podrían considerarse el material del recipiente, la estabilidad del arreglo y la presencia de elementos delicados. Estas variables todavía son una propuesta. En ambos niveles de cuidado será necesario proteger las flores durante el traslado.

## A1 - Corpus frente a intenciones

| Aspecto | Dataset de intenciones | Corpus / dataset para RAG |
|---|---|---|
| Unidad típica | Un mensaje de ejemplo y su etiqueta: «¿Dónde va mi pedido?» → rastrear_pedido. | Un fragmento de un documento del negocio; por ejemplo, una sección de la política de traslado, con su título y versión. |
| Para qué sirve en el bot | Identificar lo que necesita el cliente: saludar, consultar un pedido, conocer una política o solicitar una recomendación. | Buscar información en los documentos del negocio para responder con base en ellos. |
| Qué falla si está mal | El asistente puede confundir una consulta de seguimiento con una pregunta general y responder sin revisar el pedido. Esto puede ocurrir si los ejemplos son insuficientes o están mal etiquetados. | Puede encontrar información desactualizada, incompleta o que no corresponde a la pregunta y dar una respuesta incorrecta. |

Los dos pueden usarse en el mismo asistente. Para la floristería, primero identificaría la intención del mensaje y después decidiría si hace falta buscar un documento, consultar un pedido o solicitar una recomendación. La razón es que cada pregunta necesita una fuente distinta: una guía puede explicar el cuidado frágil, pero no indicar dónde está un pedido en este momento.

Ejemplos de funcionamiento:

1. «Hola»: responder con un saludo, sin consultar el corpus.
2. «¿Qué significa traslado frágil?»: buscar la explicación en la guía de traslado e indicar de qué documento se obtuvo.
3. «¿Dónde va mi pedido?»: solicitar el folio si falta y consultar la API de pedidos con autorización del comprador. El estado actual no se obtiene del corpus.
4. «¿Qué cuidado requiere este arreglo?»: reunir los datos necesarios y consultar al recomendador antes de responder frágil o estándar.
5. «¿Por qué mi pedido quedó como frágil?»: consultar el resultado guardado del pedido y la explicación que el sistema permita mostrar al cliente. También puede usarse la guía para explicar qué significa ese nivel de cuidado.

Si no queda claro lo que solicita el cliente, el asistente debe pedirle una aclaración antes de continuar.

3. Regla de chunking

Dividiría los documentos por secciones, procurando que cada fragmento o chunk contenga una explicación completa. Por ejemplo, mantendría juntas una pregunta y su respuesta, o una regla y sus excepciones. Usaría como referencia 150–300 palabras por fragmento, aunque una sección más breve podría conservarse tal como está.

Si una sección es demasiado larga, la dividiría conservando el título y la información necesaria para entender cada parte. Cuando sea útil, repetiría entre 30 y 50 palabras al inicio del siguiente fragmento para mantener la continuidad.

Por ejemplo, separar «se aceptan solicitudes en domingo» de «solo en las fechas y condiciones expresamente publicadas» produciría una promesa incorrecta. Deben permanecer juntas. Cada chunk llevará chunk_id, documento_id, titulo, version, vigente_desde, vigente_hasta cuando aplique, audiencia y responsable. La recuperación pública filtrará por audiencia y vigencia antes de seleccionar los fragmentos pertinentes.

## A4 - Casos límite

1. Un fragmento correcto y otro viejo se contradicen

El asistente debe revisar la versión y la fecha de vigencia de ambos documentos. Si uno sustituye al otro de manera expresa, utilizará el vigente. Si no puede determinar cuál corresponde, deberá explicar que no puede confirmar la información y remitir la consulta a atención al cliente. Que un fragmento se parezca más a la pregunta no significa que esté actualizado.

El negocio es responsable de aprobar y actualizar sus políticas. Quien mantenga el índice debe retirar las versiones anteriores, y las instrucciones del asistente deben indicar qué hacer si encuentra una contradicción. Las tres partes son necesarias: una instrucción en el prompt no basta si se siguen recuperando documentos viejos.

2. La pregunta necesita un dato vivo

El estado del pedido, su folio, el nivel de cuidado asignado y la disponibilidad actual se consultan en la base mediante una API autorizada. El corpus conserva explicaciones generales, como el significado de «frágil» o las instrucciones para buscar un folio.

Ante «¿Ya salió mi pedido?», el backend verifica el acceso del comprador y consulta el pedido. El folio identifica el registro, pero no debe asumirse como autorización suficiente para mostrar datos personales. Si la API falla, se informa que no fue posible consultar el estado; no se sustituye con un estado inventado o recuperado de un documento.

3. Alguien incorpora un .joblib o un dump de la base

El archivo .joblib contiene el modelo guardado. Incluirlo en el índice no permite usarlo para hacer una predicción y tampoco aporta una explicación que el cliente pueda consultar. Debe cargarse desde el backend y comprobarse su procedencia, ya que abrir archivos de este tipo de una fuente desconocida puede ejecutar código.

Una copia completa de la base de datos, o dump, podría incluir nombres, domicilios, teléfonos y pedidos. Además de exponer información privada, quedaría desactualizada cuando cambiaran los registros. Por estas razones, ninguno de los dos archivos debe formar parte del corpus público. Los pedidos se consultarán por API y solo se mostrarán a quienes tengan permiso.

## A5 - Criterio de calidad: rúbrica propia

Aceptaría un fragmento cuando cumpla los cinco criterios siguientes. Si le falta información, lo corregiría antes de incluirlo en el índice.

1. Vigencia identificable

Condición para aceptarlo: Incluye versión, fecha de vigencia y responsable; no está sustituido ni fuera de su periodo aplicable.

2. Audiencia y privacidad

Condición para aceptarlo: Está aprobado para compradores y no contiene datos personales, secretos ni reglas internas confidenciales.

3. Pertinencia

Condición para aceptarlo: Responde una necesidad de la floristería: productos, cuidados, entrega, seguimiento o incidencias.

4. Integridad y claridad

Condición para aceptarlo: Trata una unidad comprensible y conserva condiciones, excepciones y referencias necesarias.

5. Trazabilidad

Condición para aceptarlo: Tiene identificador y fuente aprobada que permite verificar la afirmación; distingue orientación general de datos que requieren API.

## A6 - Desacoplamiento por API

Para explicar la comunicación entre los componentes, propongo las siguientes rutas. Se definirán al desarrollar el backend. BASE_API representa la dirección del servidor o del gateway.

1. Tres caminos y sus responsables

Camino 1: mensaje y respuesta del chat.

```text
[Flutter: interfaz del comprador]
        | POST BASE_API/entregas/asistente/
        | {mensaje, identificador_de_sesion}
        v
[Backend: orquestador del asistente]
        | Clasifica la intención y selecciona el flujo
        v
[Respuesta HTTP JSON: intencion, respuesta, fuentes]
        |
        v
[Flutter: muestra la respuesta]
```

Flutter se encarga de mostrar la conversación y enviar los mensajes por HTTP. El backend identifica la intención, consulta lo necesario y prepara la respuesta. El identificador de la conversación sirve para distinguir el chat; para acceder a un pedido también hace falta comprobar la identidad del comprador.

Camino 2: recuperación documental.

```text
[Orquestador del backend]
        | Consulta documental
        v
[Módulo RAG en el servidor]
        | Filtra audiencia y vigencia; busca fragmentos
        v
[Índice y chunks públicos aprobados, almacenados en servidor]
        | Fragmentos pertinentes + referencias
        v
[Orquestador: redacta con evidencia o informa falta de información]
```

El módulo RAG y los documentos se mantienen en el servidor. Al principio podrían formar parte del mismo backend; si después se separan en un microservicio, se consultarían mediante una API interna. Flutter solo recibe la respuesta y las referencias que se puedan mostrar al cliente.

Camino 3: consulta del estado actual.

```text
[Flutter: envía una pregunta de seguimiento al chat]
        |
        v
[Orquestador: identifica seguimiento y comprueba datos requeridos]
        | GET /api/pedidos/{folio}/ con contexto de autorización
        v
[Módulo de pedidos: verifica acceso y consulta SQLite]
        | Estado y datos autorizados del pedido
        v
[Orquestador: prepara respuesta] --> [Flutter]
```

El módulo de pedidos consulta SQLite y comprueba que el comprador tenga permiso para ver el registro. Puede formar parte del mismo backend o funcionar como un servicio separado. En ambos casos, Flutter se comunica por HTTP con el servidor, sin abrir la base de datos. El estado del pedido se obtiene de esa consulta.

3. ¿Incluir el índice RAG en el APK?

No incluiría el índice RAG en el APK. Cuando cambiara una política, algunas instalaciones conservarían la información anterior hasta actualizar la aplicación. También aumentaría el tamaño del archivo y su contenido podría extraerse del paquete.

Mantendría el índice en el servidor para actualizar los documentos sin tener que reinstalar la aplicación. Haría lo mismo con el .joblib, de modo que todos los clientes consulten la versión del modelo que esté en uso y se apliquen las mismas reglas.

4. Si hay gateway, ¿con quién habla el chat?

Flutter se comunicaría con el gateway, que recibiría la petición y la enviaría al servicio del asistente. Desde allí se consultaría el corpus, el pedido o el recomendador según la pregunta del cliente.

Así, la aplicación no tendría que conocer la dirección de cada servicio. Si cambia la organización del backend, se podría ajustar el gateway sin modificar todas las llamadas de Flutter. El gateway también puede comprobar la autenticación, aunque cada servicio debe seguir verificando los permisos de las operaciones que realiza.
